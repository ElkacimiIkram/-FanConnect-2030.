2. Contexte et problématique

2.1 Organisme d’accueil

GM-Soft (German Moroccan Software Company) est une SSII maroco-allemande (SARL, 2014) basée à Béni Mellal. Solutions : GM-ERP, GM-POS, GM-CAFE, GM-HOTEL. FanConnect 2030 prolonge GM-CAFE : digitaliser le café le jour de match (calendrier sportif, géolocalisation, réservation, paiement, occupation prédictive).

2.2 Contexte métier

À l’approche de la Coupe du Monde 2030 au Maroc, les supporters cherchent un lieu proche et disponible. Les cafés n’ont pas d’outil unifié : WhatsApp et le téléphone restent la norme. Il n’existe pas de lien fiable entre le calendrier football, la table du café et l’occupation réelle.

2.3 Problématique

Comment concevoir une plateforme fiable, sécurisée et intelligente permettant aux supporters de réserver un lieu adapté pour un match, tout en aidant les cafés à anticiper l’affluence — dans le contexte de la CDM 2030 ?

AxeQuestion de conception
MétierUnifier match, lieu, table et paiement dans un seul parcours
OccupationEstimer l’affluence avant le coup d’envoi (owner + réservations + IA)
ArchitectureSéparer API métier, interface et service d’apprentissage

4. Périmètre

4.1 Inclus

  • SPA React responsive — trois espaces Fan / Owner / Admin
  • API REST Spring Boot 3, Java 21, JWT, OpenAPI
  • PostgreSQL 16, Flyway
  • Synchronisation des matchs (football-data.org)
  • Réservation d’une table d’un café APPROVED pour un match
  • Paiement Stripe mode test (ou simulé si clés absentes)
  • Ticket QR unique + PDF + check-in
  • Occupation live (rapport owner + réservations pondérées)
  • Prédiction d’occupation (Python Random Forest ou heuristique)
  • Recommandation de cafés (5 / 10 / 20 km + affluence)
  • KYC : CIN + registre de commerce + photo de façade
  • Notifications in-app, Docker Compose

4.2 Exclus

  • Application mobile native
  • Stripe live (production réelle, virement owner)
  • Billetterie de stade / places FIFA
  • Remboursement automatique Stripe (seul le statut métier REFUNDED)
  • Multi-devises hors MAD, chat vocal, borne physique

4.3 Hypothèses

  • H1 — Une table est unique par match (PENDING ou CONFIRMED).
  • H2 — Le ticket n’existe qu’après paiement PAID → CONFIRMED.
  • H3 — Seuls les cafés APPROVED sont visibles et réservables.
  • H4 — Le propriétaire peut saisir un effectif physique (walk-in).

8. Exigences fonctionnelles

Priorité : M Must, S Should, C Could. Chaque exigence est testable.

EF01 — Inscription et authentification JWT  |  M  |  Tous

Compte Fan ou Owner, JWT, rôle dans le token. Email unique. Mot de passe BCrypt. ADMIN interdit à l’inscription publique. Fan : ville obligatoire. Token HS256, localStorage, header Bearer.

Acceptation : Fan → 201 + JWT ; email déjà utilisé → 400 ; rôle ADMIN → 400 ; login faux → 401 ; Fan sur /admin/** → 403.

EF02 — Match Center  |  M  |  Fan (lecture publique)

Matchs synchronisés football-data.org, stockés en PostgreSQL, upsert par externalId. Sync ~60 s (J→J+7 + LIVE), compétitions ~5 min. Cache 10/15/30 s. API down : données locales. FINISHED / CANCELLED non réservables.

EF03 — Recherche des cafés  |  M  |  Fan

Uniquement APPROVED. Occupation RM-OCC. VERT ≤ 50 %, ORANGE ≤ 80 %, ROUGE > 80 %. PENDING / DISABLED invisibles.

EF04 — Réservation d’une table (wizard)  |  M  |  Fan

Match + café + espace + table + partySize. Création atomique Reservation PENDING + Payment PENDING (MAD). Contrôles : APPROVED, match réservable, table active, partySize ≤ capacité, table non déjà PENDING/CONFIRMED pour ce match. Prix = matchDayPrice. Pas de ticket à ce stade.

Include UML : Auth, Match, Café, Disponibilité, Paiement.

EF05 — Paiement en ligne  |  M  |  Fan + Stripe

Carte jamais sur nos serveurs (PCI-DSS Stripe). Commission 25 % : fee = amount × 0,25 ; payout = amount − fee. MAD, centimes. PaymentIntent metadata reservationId. Le backend revérifie Stripe (succeeded + metadata). Succès : PAID + CONFIRMED + ticket. Mode simulé si clés absentes. Include ticket. Extend paiement simulé.

EF06 — Ticket QR, PDF, identifiant  |  M

FC- + 8 car. UUID. QR : FANCONNECT|TICKET|{code}. PDF : match, café, table, partySize, montant, QR. Pas de ticket si non PAID. Parser : payload complet ou code seul.

EF07 — Recommandation de cafés  |  S

GPS optionnel. Rayons 5 → 10 → 20 km jusqu’à ≥ 3 résultats. Score distance + occupation. APPROVED seulement.

EF08 — Prédiction d’occupation  |  S

Pic 1 h / 2 h / coup d’envoi ; risque LOW / MEDIUM / HIGH. Python Random Forest si dispo, sinon heuristique (+12 CDM, +8 week-end, +6 soirée, historique 30 j, vitesse check-in). UI n’appelle pas Python. Extend de Consulter l’occupation.

EF09 — Établissement et KYC  |  M  |  Owner

Création PENDING (invisible). Documents obligatoires : CIN, RC, photo façade. Soumission incomplète → 400. Notif admins. Include Déposer documents.

EF10 — Occupation live  |  M  |  Owner

Saisie OWNER_MANUAL. Check-in : CHECK_IN_AUTO + partySize, plafond capacité. Fraîcheur 15 min. Isolation owner.

EF11 — Ticket et check-in  |  M  |  Owner

ticketCode ET owner du café. PENDING/CANCELLED invalide. CHECKED_IN déjà utilisé. CONFIRMED : check-in possible. On peut vérifier sans faire entrer → extend [CONFIRMED].

EF12 — Modération admin  |  M

Include Consulter le dossier. Approuver si 3 pièces : APPROVED + géocodage + notif. Rejeter + motif, resoumission possible. DISABLED retiré des fans. Extend Approuver / Rejeter.

EF13 — Pilotage admin  |  S

Users, compétitions, heatmap, top cafés, commissions, analytics, désactivation.

EF14 — Notifications  |  S

Paiement, nouvelle résa, commission, check-in, café approuvé / rejeté / désactivé.

EF15 — Annulation  |  S

Interdite si CHECKED_IN. PAID → REFUNDED métier (pas de refund Stripe auto). Extend Gérer mes réservations.

EF16 — FanBot  |  C

Aide match / café. Non bloquant. Extend Réserver [aide].

9. Règles métier

9.1 RM-OCC — Occupation effective

ConstanteValeurSens
ARRIVAL_RATE0,85% des CONFIRMED encore attendus
PAYMENT_RATE0,60% des PENDING qui paieront
FRESHNESS15 minValidité du rapport owner
GREEN / ORANGE50 % / 80 %Seuils de couleur
estimationRésa = checkedIn + round(confirmed × 0,85) + round(pending × 0,60)

Si rapport owner ≤ 15 min : effectif = ownerReported (vérité terrain, walk-in inclus). Sinon : effectif = estimationRésa. Plafond capacité. % = effectif / capacité × 100.

Exemple de recette : café 100 places, 20 check-in, 40 confirmés, 10 pending, owner = 55 il y a 8 min. estimationRésa = 60 mais rapport frais → effectif = 55, walk-in ≈ 35, pic = 89 %.

Ne pas simplifier le jour de match en booked/capacity.

9.2 RM-PAY

fee = amount × 0,25     payout = amount − fee     currency = MAD

Retrieve Stripe obligatoire (succeeded + metadata reservationId).

9.3 RM-TCK

ticketCode = "FC-" + UUID[0..8].upper()
qrPayload  = "FANCONNECT|TICKET|" + ticketCode

9.4 RM-KYC

PENDING → (3 pièces + soumission) → APPROVED | REJECTED | DISABLED

Seul APPROVED est visible et réservable. APPROVED déclenche le géocodage.

9.5 RM-RES

PENDING → CONFIRMED → CHECKED_IN     (ou CANCELLED avant check-in)

Une table, un match, au plus une résa active PENDING ou CONFIRMED.

16. Sécurité

  • JWT stateless (signature, expiration, UserDetails)
  • Autorisation par rôle
  • Isolation owner (business.ownerId, tickets du café)
  • Un seul check-in par ticket
  • Vérification serveur du PaymentIntent
  • ADMIN non créable en public
  • Uploads KYC hors web root
  • CORS limité ; CSRF désactivé (API JWT) à documenter
